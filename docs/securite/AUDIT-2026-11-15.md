Demande du porteur : authentification réelle, secrets protégés, base sécurisée, HTTPS, mots de passe hachés, validation côté serveur, XSS,
journal des activités suspectes, routes d'administration verrouillées, requêtes paramétrées, variables d'environnement, limite de requêtes,
en-têtes, cookies, CSRF, liens de réinitialisation, fichiers envoyés, paiements, mode débogage, dépendances, fichiers exposés, historique Git.
Chaque point a été vérifié dans le code et, quand c'était possible, par des requêtes réelles sur le serveur lancé en mode production.

## Ce qui était déjà en place, vérifié

- Mots de passe hachés (PBKDF2 de Django), comparaison en temps constant, même réponse pour un identifiant inconnu et un mauvais mot de passe.
- Session : cookie signé, HttpOnly, SameSite Strict, Secure en ligne, durée d'une journée de travail, nouvelle clé à chaque connexion, jeton révocable (déconnexion forcée).
- CSRF : toute écriture exige l'en-tête propre à l'application, en plus du cookie SameSite Strict ; un refus est noté au journal.
- Requêtes paramétrées partout ; les seuls noms insérés dans le SQL viennent de listes fixes du code.
- Validation côté serveur de chaque saisie ; un refus annule toute la requête (T21).
- XSS : React échappe tout ; aucun HTML brut ; images acceptées seulement en PNG ou JPEG, 300 Ko au plus.
- HTTPS : imposé par Firebase Hosting et Cloud Run ; HSTS ajouté.
- Secrets : dans Secret Manager ; déploiement sans clé (Workload Identity) ; mode débogage coupé par défaut.
- Historique Git : aucun mot de passe, aucune clé, aucune adresse de base avec mot de passe ; seulement des exemples.
- Python : `pip-audit` sans faille connue.

## Sans objet aujourd'hui

- Liens de réinitialisation du mot de passe : le logiciel n'en envoie pas ; l'administrateur change le mot de passe (Administration > Utilisateur).
- Prix et paiements en ligne : le logiciel n'encaisse rien en ligne ; tous les montants sont recalculés et contrôlés par le serveur.
